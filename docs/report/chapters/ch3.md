# CHAPTER 3: ANALYSIS AND DESIGN

## 3.1 Introduction

The previous chapter established that university timetabling is a hard but well-understood problem, that constraint programming is a sound way to attack it, and that the gap worth filling is not the solver itself but the system around it — one that reflects how a university such as Buea is actually organised and how the people responsible for a timetable actually work together. This chapter turns that conclusion into a concrete plan for the software.

It does so in the order an engineer would follow. It first describes the methodology that shaped the development, then analyses what the system must do, separating the requirements into the functions it must provide and the qualities it must possess. From that analysis it moves to design: the data are modelled with an entity–relationship diagram, the behaviour the users expect is captured in use case diagrams, the software structure is described with a class diagram, and the three processes that matter most — generating a timetable, getting it approved, and editing it by hand — are traced through sequence and activity diagrams. The chapter then sets out the global architecture of the solution, before describing in detail the constraint model at its centre and the resolution process by which a request for a timetable becomes a published schedule. A partial conclusion closes the chapter and leads into the implementation described in Chapter 4.

Throughout, the design is kept faithful to a single guiding decision taken in Chapter 1: the system must enforce the hard scheduling rules itself, so that no invalid timetable can reach a human, and it must wrap that guarantee in a workflow and a structure that match the university rather than forcing the university to match the software.

## 3.2 Methodology

The work followed an iterative, incremental engineering process rather than a single large design-then-build effort. The reason was practical. The riskiest part of the project was not the user interface but the scheduling engine, where it was not obvious in advance that a constraint solver could express every rule of university timetabling and still return an answer in a usable time. Committing to a complete design before testing that assumption would have been unwise. The system was therefore built in slices, each one a thin but working path through the whole stack, with the scheduling core tackled first.

The process can be described in five overlapping stages.

The first stage was **requirements analysis**. The rules and data of timetabling were drawn out by examining how the process is carried out manually at the Faculty of Engineering and Technology and by reading the literature surveyed in Chapter 2. Each rule was classified as a hard constraint that the system must guarantee or a soft preference that it need not, and each thing a user might want to do was recorded as a candidate function. The output of this stage is the set of requirements in Section 3.3.

The second stage was **modelling and design**. The data were modelled as an entity–relationship diagram, and the software was described in the Unified Modeling Language through use case, class, sequence, and activity diagrams. These models, presented in Section 3.4, were not drawn once and frozen; they were revised whenever building a slice revealed that the model was wrong or incomplete.

The third stage was **construction of the scheduling core**. University timetabling was formulated as a constraint satisfaction problem and encoded for Google's OR-Tools CP-SAT solver. This was done early and in isolation, tested against small hand-checked instances before any interface was built around it, so that the central assumption of the project could be validated before effort was spent elsewhere.

The fourth stage was **incremental implementation** of the rest of the system around that core: the data model and its management screens, the role-based access control, the generation job, the approval workflow, and the public distribution of the result. Each capability was added, tested, and integrated before the next was begun. The backend was built with FastAPI and the frontend with Flutter, communicating over a REST/JSON interface.

The fifth stage was **evaluation**, in which the assembled system was exercised with realistic data and assessed against the objectives of Chapter 1 and against the manual process it replaces. The results of that evaluation are reported in Chapter 4.

These stages were not strictly sequential. In practice the work moved repeatedly between them — a difficulty met during implementation would send the work back to the design, and a clarified requirement would change what was built next. This is the normal rhythm of building software whose hardest part is understood only by attempting it.

## 3.3 Analysis

Analysis answers two questions: what the system must do, and how well it must do it. The first is captured as functional requirements, the second as non-functional requirements. Both were derived from the problem statement of Chapter 1 and from the way timetabling is actually carried out at the university.

### 3.3.1 Functional Requirements

The functional requirements describe the services the system must provide to its users. They are grouped here by the area of the system they concern.

**Management of academic data.** The system must allow an administrator to record the full academic structure of a university: its faculties, the departments within each faculty, the levels within each department, and the classes at each level, each class carrying the number of students it contains. It must allow the recording of the physical resources — buildings and the rooms within them, each room with its capacity and its type (lecture hall, laboratory, or outdoor space) — and of the academic calendar, namely the semesters and the time slots of the teaching week. It must allow courses to be recorded, each course carrying the type of room it requires and the number of weekly sessions it needs, and each course belonging either to a level of a department or to the university as a whole. It must allow lecturers to be recorded and assigned to the courses they teach, and it must allow a class that is too large for laboratory work to be divided into groups.

**User and access management.** The system must support six categories of user — super administrator, university administrator, faculty head, timetable officer, lecturer, and student — and must grant each only the actions appropriate to their role. It must allow a super administrator to create universities and their administrators, an administrator to create and manage the users of their university, including the bulk import of staff from a file, and every account-holder to log in and to change their password. Because several actions are scoped to one part of the university, the system must record which part each user belongs to — a faculty head to the faculty they govern, a lecturer to their department — and a faculty may have only one acting head, so that responsibility for approving its timetable is never ambiguous. Students, by design, hold no account.

**Timetable generation.** The system must allow a timetable officer to define a timetable run by choosing a semester, the faculties it covers, and the buildings whose rooms it may use. It must then generate, on request, a complete weekly timetable for that run automatically, assigning every course session to a lecturer, a room, and a time slot in such a way that no hard constraint is broken. Before it attempts to generate, the system must satisfy itself that the run can in principle succeed — that the courses in scope have lecturers assigned, that the chosen buildings hold rooms of the types those courses require, and that the semester has time slots defined — and must refuse, with a clear account of what is missing, rather than produce an empty or partial timetable that wears the appearance of success. Because generation may take time, it must run in the background and report its progress, so that the officer is not left staring at a frozen screen. Where the data make a valid timetable impossible — for instance, a laboratory class that cannot be split into enough groups for the sessions available — the system must not fail silently but must record the problem as a conflict for a person to resolve.

**Review, approval, and publication.** The system must let the timetable officer submit a generated draft for review, and must then require the head of each faculty covered by the run to approve or reject the portion concerning their faculty. A run may only become approved when every faculty head has approved it; a single rejection must return it to the officer for correction. Only an approved run may be published, and publication must notify the people concerned and make the timetable available on a public page.

**Conflict resolution and manual adjustment.** The system must provide the means to resolve the conflicts flagged during generation, in particular laboratory-splitting conflicts, which it must allow an officer to settle either by adding an extra weekly session or by rotating groups across alternating weeks. It must also allow an officer to move an individual session to a different slot or room by hand, and it must check that change for clashes before accepting it, rejecting any move that would double-book a lecturer or a class.

**Distribution and export.** The system must publish an approved timetable to a view that students can reach without an account, through a shareable link, and that can be filtered down — by faculty, then department, then class — so that a student sees only their own schedule. It must also allow timetables to be exported as PDF and CSV files for printing and record-keeping, and it must notify users of the events that concern them, such as the publication of a timetable or a request for review.

**Monitoring.** The system must provide a role-aware dashboard and basic analytics over a generated timetable — for example the number of sessions per lecturer, the count of over-capacity placements, and the utilisation of rooms — so that the people responsible can judge the quality of a result at a glance. Access to the analytics must follow that responsibility: a university administrator sees them for the whole university, a faculty head only for their own faculty, while the timetable officer, who produces a timetable rather than answering for it, is not given them.

### 3.3.2 Non-Functional Requirements

The non-functional requirements describe the qualities the system must have, independent of any single function.

**Correctness.** This is the foremost requirement. A published timetable must contain no violation of a hard constraint. The system must guarantee this not by checking a result after the fact but by construction, so that an invalid arrangement cannot be produced in the first place. Correctness here is not a matter of degree: a timetable that double-books a single lecturer has failed.

**Performance.** Generation must complete in a time that makes the system usable in practice — a matter of seconds to a couple of minutes for a realistically sized faculty, not hours. The solver is therefore given a bounded time in which to work, and the rest of the system is designed so that ordinary operations, such as loading a timetable or moving a session, respond promptly.

**Security.** Access to every action must be governed by the user's role, enforced on the server and not merely hidden in the interface. Passwords must be stored only in hashed form, never in plain text, and authenticated sessions must be carried by signed tokens. The data of one university must be kept separate from those of another, and within a university, a faculty head sees only the runs and academic data of their own faculty.

**Usability.** The intended users are university staff and students, not engineers. The interface must be clear enough that a timetable officer can generate and publish a schedule, and a student can find their class, without training. The result must be legible on the devices people actually use, which in this setting means the web on a desktop and a phone alike; the interface therefore adapts its layout to the size of the screen.

**Reliability.** Generation runs as a background job whose state is recorded, so that a failure leaves a clear record rather than an unexplained absence of result. Operations that change data are transactional, so that a partial failure does not leave the database in an inconsistent state.

**Maintainability and extensibility.** The system is built in clearly separated layers — data, business logic, scheduling engine, and interface — so that one can be changed without disturbing the others. The data model holds more than one university, with each kept apart, so that the system is not tied to a single institution and can be deployed elsewhere without redesign.

**Portability.** The frontend is built from a single codebase that runs on the web and on mobile devices, and the backend depends only on open-source components, so that the system can be hosted without proprietary licences.

## 3.4 Design

The design translates the requirements of the previous section into models of the system's structure and behaviour. The data are modelled first, since everything else rests on them, followed by the actors and their use cases, the software structure, and finally the dynamics of the three central processes.

### 3.4.1 Entity–Relationship Model

The entity–relationship diagram in Figure 3.1 describes the data the system stores and the relationships among them. It is organised around four groups of entities: the academic hierarchy, the physical and temporal resources, the people, and the timetable runs that tie everything together.

The **academic hierarchy** begins with the *University*, which owns one or more *Faculties*. Each faculty contains *Departments*, each department contains *Levels* (the 100, 200, 300 and higher years of study), and each level contains *Classes*. A class records its student *population*, the figure on which all capacity decisions depend, and may be divided into *ClassGroups* for laboratory work. This chain — University → Faculty → Department → Level → Class → ClassGroup — mirrors exactly the structure of a Cameroonian university and is the structure that, as Chapter 2 noted, existing tools fail to match.

The **physical and temporal resources** sit alongside the hierarchy. A university owns *Buildings*, each of which contains *Rooms*; a room records its *capacity* and its *room\_type*. A university also owns *Semesters*, each marked as the first or second *term* of its academic year and divided into *TimeSlots*, the discrete periods of the teaching week into which sessions are placed.

*Courses* connect the hierarchy to the people and resources. A course records the *room\_type\_required* for it and its *weekly\_hours*, records which *semester* of study it runs in (first, second, or year-long), and belongs either to a level of a department or, for university-wide courses, to the university directly. A course may be taught by a *Lecturer*, and it may be shared with classes other than its own through the *SharedCourse* relationship, which is what allows one lecture to serve several classes at once.

The **people** are modelled through a single *User* entity carrying the credentials, the *role*, and the institutional links common to every account-holder. Two specialisations extend it: a *Lecturer*, who belongs to a department and whose unavailable periods are recorded in *LecturerAvailability*, and a *Student*, who belongs to a class or group. As decided in Chapter 1, students in the final design hold no account, so the *Student* entity is retained in the model but not used as a login.

Finally, the **timetable run** binds these together. A *TimetableRun* belongs to a semester and records its *status* as it moves from draft to published. Its scope is set by the *TimetableRunFaculty* and *TimetableRunBuilding* link tables, which record the faculties it covers and the buildings whose rooms it may use. The result of generation is stored as *TimetableEntry* rows — each one a single session, linking a course, a lecturer, a room, and a time slot, and marked if it is over capacity or merged — with a *TimetableEntryClass* link table recording the one or more classes that attend it. Around the result sit the *GenerationJob* that produced it, the *TimetableConflict* records of problems found during preprocessing, the *FacultyHeadApproval* records that drive the review workflow, and the *Notification* records that keep users informed.

### 3.4.2 Use Case Model

The use case diagram in Figure 3.2 shows what each kind of user can do with the system. Six actors appear, corresponding to the six roles, and they form a hierarchy of responsibility rather than a flat list.

The **Super Admin** stands above any single university: their concern is to create universities and to provision each with its first administrator. The **University Admin** governs one university, setting up its buildings and rooms, its semesters and time slots, its academic structure, and its courses, and managing its users — including the bulk import of staff from a file, which spares an administrator from entering dozens of accounts by hand.

The **Faculty Head** is accountable for the academic data of a faculty and, crucially, is the actor who reviews and approves the portion of a timetable concerning their faculty. The **Timetable Officer** is the operational heart of the system: they create a timetable run, generate it, resolve any conflicts it raises, move sessions by hand where necessary, submit the draft for review, and, once it is approved, publish it and export it.

The **Lecturer** has a narrow set of actions — declaring their unavailability, which the generator respects, and viewing their own schedule. The **Student** has the narrowest of all: viewing the published public timetable, filtered to their own class, without logging in.

What each actor may *see* of a run depends on how far it has progressed. A draft belongs to the officer and the administrators alone; a faculty head and a lecturer see a run only once it is under review, and again once it is published, so that work still in progress is not exposed before it is ready to be judged.

Several use cases are shared across the account-holding roles, notably logging in, changing a password, and receiving notifications. The diagram also records a few relationships among use cases: submitting for review *includes* the act of putting the run before the faculty heads; publishing *includes* the notifications it fires; and generation may *extend* into conflict resolution when the data make a clean timetable impossible.

### 3.4.3 Class Diagram

The class diagram in Figure 3.3 describes the software structure in two parts: the domain model, which mirrors the entities of Figure 3.1 as the classes the application manipulates, and the solver layer, which contains the classes that turn stored data into a timetable.

In the **domain model**, each class corresponds to a table in the database and carries the attributes relevant to behaviour. Most of these classes are containers of data and relationships, but a few carry behaviour of their own: a *TimetableRun* can be submitted for review and published, a *FacultyHeadApproval* can be approved or rejected. The associations among them — composition for parts that cannot exist without their whole, such as a *TimetableEntry* within a *TimetableRun*, and plain association for references such as the *Course* an entry points to — express the same structure as the entity–relationship model, now in the vocabulary of objects.

The **solver layer** is deliberately kept separate from the domain model, so that the scheduling logic does not depend on the database and can be tested on its own. The *DbPreprocessor* reads the domain model and produces a *SolverInput*, a plain data structure containing the list of *ScheduleSession* objects to place, the available time slots and rooms, and the lecturers' unavailability. In doing so it consults the *Preprocessor*, whose two operations decide how shared courses are merged and how large laboratory classes are split. The *CpSatSolver* takes the *SolverInput* and returns a *SolverResult*; it knows nothing of databases or HTTP. The *Postprocessor* writes that result back into the domain model as *TimetableEntry* rows, and the *ConflictResolver* applies an officer's chosen resolution to a flagged conflict. This separation — domain on one side, solver on the other, joined only by simple data structures — is what makes the scheduling core independently testable and replaceable.

### 3.4.4 Sequence Diagrams

Five interactions are described here by sequence diagrams showing how the parts of the system collaborate over time. The first, authentication, underlies every other action; the remaining four trace the processes that carry most of the system's value — generation, conflict resolution, approval, and manual editing.

**Authentication and authorisation.** Figure 3.4 traces how a user is admitted to the system and how each later request is checked. At login, the server looks up the account, verifies the password against its stored hash, and — only if the account exists, the password matches, and the account is active — issues a signed token, which the client keeps in secure storage. Every subsequent request carries that token. The server decodes and verifies it, loads the user it identifies, and then checks that the user's role permits the action requested, refusing with an unauthorised response if the token is invalid and a forbidden response if the role is insufficient. This is the mechanism behind the security requirement of Section 3.3.2: the rules are enforced on the server for every request, not merely reflected in what the interface chooses to show.

> **Figure 3.4** — Sequence diagram for login and role-based authorisation (source: `diagrams/seq_auth.puml`).

**Generation.** Figure 3.5 traces what happens when an officer asks for a timetable. The request does not block: the router checks that the run is a draft, records a generation job, schedules the actual work as a background task, and returns immediately, leaving the client to poll for progress. The background task drives the three-stage core. The *DbPreprocessor* loads the data and builds the solver input, deciding along the way which courses to merge and which laboratory classes to split, and any problem it cannot resolve is stored as a conflict. The *CpSatSolver* then builds its constraint model and searches for a valid assignment. If it succeeds, the *Postprocessor* writes the assignments into the database as timetable entries and the job is marked complete; if it fails, the job records the reason. Either way the officer is notified, and the client, on its next poll, loads and displays the result.

> **Figure 3.5** — Sequence diagram for automatic timetable generation (source: `diagrams/seq_generation.puml`).

**Conflict resolution.** Generation flags a conflict whenever the data make part of the timetable impossible — most often a laboratory class that needs more groups than the week has sessions — but it does not decide what to do about it, because that is a teaching judgement. Figure 3.6 traces how an officer settles such a conflict. The officer opens the conflicts screen, where each flagged problem is shown with the two resolutions available. Choosing *add session* hands the conflict to the resolver, which finds a free slot that clashes with neither the lecturer nor the class, finds a suitable laboratory, and inserts the extra sessions needed to accommodate the missing groups. Choosing *rotate groups* instead leaves the number of sessions unchanged and marks the course's entries with a rotation pattern, so that the groups alternate across weeks. In either case the conflict is then marked resolved, and the timetable is complete.

> **Figure 3.6** — Sequence diagram for resolving a laboratory-splitting conflict (source: `diagrams/seq_conflict.puml`).

**Approval and publication.** Figure 3.7 traces the workflow that turns a draft into a published timetable. When the officer submits a run, the system first checks that every faculty in the run has an active head to approve it — there is no point asking for an approval that no one can give — and then creates a pending approval record for each faculty, moves the run to *under review*, and notifies the heads. Each head then acts independently on their own faculty's section. An approval that completes the set advances the whole run to *approved*; a single rejection returns the run to *draft* so the officer can correct and resubmit it. Only once the run is approved may the officer publish it, at which point the people concerned are notified and the run appears on the public page.

> **Figure 3.7** — Sequence diagram for the review, approval, and publication workflow (source: `diagrams/seq_approval.puml`).

**Manual move with clash detection.** Figure 3.8 traces the most safety-critical of the editing operations. When an officer drags a session to a new slot, the change is not applied blindly. The router loads the entry, then checks whether the lecturer already has a session in the target slot, and whether any of the classes attending the session already have one there. If either check finds a clash, the server refuses the move with an explicit conflict response, and the interface shows the reason inline and leaves the session where it was. Only when both checks pass is the move committed. The guarantee made at generation — that no invalid timetable can exist — is thus preserved through manual editing, because the same rules are enforced at every point where the timetable can change.

> **Figure 3.8** — Sequence diagram for a manual session move with clash detection (source: `diagrams/seq_move.puml`).

### 3.4.5 Activity Diagrams

Where the sequence diagrams show which components talk to which, the activity diagrams show the flow of the work itself, including its decisions and its branches.

Figure 3.9 describes the **generation activity** from end to end. After the officer triggers a run, the preprocessing stage iterates over the courses, and for each one decides between two paths: a laboratory course is split into groups, with a conflict flagged if more groups are needed than there are sessions in the week, while an ordinary course is either merged across the classes that share it, when their combined population fits a single room within the overflow allowance, or scheduled as separate sessions when it does not. The solving stage then builds the boolean variables and the hard constraints and searches within its time limit. A feasible result flows into postprocessing, where the assignments are written and over-capacity or merged entries are flagged; an infeasible one is recorded as a failure. Either outcome ends with the officer being notified and reviewing the grid.

> **Figure 3.9** — Activity diagram for timetable generation (source: `diagrams/activity_generation.puml`).

Figure 3.10 describes the **approval activity** as a flow across three responsibilities — the officer, the system, and the faculty heads — using partitions to make clear who does what. The officer prepares and submits a draft, resolving any conflict first. The system validates the submission, creates the approvals, and notifies the heads. Each head approves or rejects; the system routes a rejection back to draft and an approval onward, advancing the run only when the last faculty has approved. The officer then publishes, and the system exposes the result publicly. Reading the two activity diagrams together gives the full life of a timetable, from the officer's first request to the moment a student can open it.

### 3.4.6 User Interface Design

The interface is designed around the roles rather than around the database, so that each user is shown the work that is theirs and little else. It is built as a single responsive application that adapts its layout to the width of the screen: a persistent sidebar on a wide desktop display, a compact navigation rail on a medium one, and a bottom navigation bar on a phone. This matters in the Cameroonian setting, where staff may work at a desktop but students will almost always reach the public timetable on a phone.

After logging in, a user arrives at a dashboard whose contents depend on their role, offering the quick actions and the summary figures relevant to them. From there the main areas of the application are reachable: the management screens, organised as tabs for buildings, users, semesters, and courses, through which an administrator maintains the data; the faculty-setup screen, which presents the academic hierarchy as a navigable tree of faculties, departments, levels, classes, courses, and groups; the timetable screen, which lists the runs and presents a selected one as a weekly grid with the controls to generate, submit, approve, publish, filter, and edit it; the conflicts screen, where flagged problems are resolved; and the public timetable, which an unauthenticated visitor reaches through a shared link and narrows to a single class with a faculty–department–level filter.

A consistent visual language ties these screens together: a royal-blue primary colour with an ember-orange accent, the Inter typeface, and Material 3 components. The aim throughout is that the structure of the interface should reflect the structure of the work, so that a user always knows where they are and what they may do. The concrete appearance of these screens is shown through screenshots in Chapter 4.

## 3.5 Global Architecture

The system is built as a client–server application with a clear separation between the device a user holds and the server that holds the data and does the heavy work. Figure 3.11 shows the arrangement.

The **client** is a Flutter application, written in Dart from a single codebase and deployed to the web and to mobile devices. It is responsible for presentation and interaction only: it renders the screens described above, collects the user's input, and calls the server. State, routing, and dependency injection are handled with GetX, and communication with the server uses the Dio HTTP client. Authentication tokens are kept in secure storage on the device. The client holds no business rules of its own; every decision that matters is made on the server, so that the rules cannot be bypassed by tampering with the client.

The **server** is a FastAPI application written in Python. It exposes a REST interface over HTTP, exchanging JSON. Internally it is layered. A routing layer receives each request, authenticates it from its token, and checks that the user's role permits the action. Below it, the business logic enforces the workflow — the transitions of a run from draft to published, the rules of approval, the clash checks on a manual move. Beneath that, an object–relational layer, built with SQLAlchemy, maps the domain model onto the database, with Alembic managing changes to the schema over time. The database itself is SQLite in the development configuration, chosen for simplicity, behind the same interface that a larger database would present.

Set apart from the request-handling layers is the **scheduling engine** described in Section 3.4.3: the preprocessor, the OR-Tools CP-SAT solver, and the postprocessor. Because generation can take longer than a web request should, it does not run inside the request that triggers it. Instead the request records a job and returns, and the engine runs as a background task, writing its result and its status back to the database, where the client finds it by polling. Two further server-side facilities support the whole: a notification mechanism that records messages for users as workflow events occur, and an export facility, built with ReportLab, that renders a timetable as a PDF or a CSV file.

The flow of a typical interaction follows this architecture directly. A user acts in the Flutter client; the client sends a JSON request to the FastAPI server; the server authenticates and authorises it, applies the relevant business logic, reads or writes the database through the ORM, and returns a JSON response; the client updates what the user sees. For generation, the same flow starts the work, but the answer arrives later, by polling, once the background engine has finished.

## 3.6 Description of the Algorithms

The intelligence of the system lies in how it turns the stored academic data into a valid timetable. This happens in three stages — preprocessing, solving, and postprocessing — of which the middle stage is the constraint model itself.

### 3.6.1 Preprocessing

The solver does not work directly on courses and classes. It works on *sessions*: individual meetings, each needing one lecturer, one room of a given type, and one time slot. The job of preprocessing is to turn the courses of the selected faculties into the exact list of sessions to be scheduled, and in doing so it makes two decisions that a naïve translation would miss. It first narrows the courses to those belonging to the run's semester — matching each course's semester against the run's term, and keeping year-long courses in both — so that a first-semester run never schedules second-semester courses.

The first is **merging**. When a course is shared among several classes — a common situation for foundational courses taught to a whole level — it would be wasteful, and often impossible, to schedule a separate lecture for each class. Preprocessing therefore considers the combined population of all the classes that take the course and the capacity of the largest suitable room, enlarged by an *overflow threshold* set per university. If the combined population fits within that enlarged capacity, the course is scheduled once as a single merged session that all the classes attend together; if it does not, the classes are scheduled separately. The overflow threshold is what lets a university decide how much crowding it will tolerate in exchange for fewer separate lectures.

The second is **laboratory splitting**. A laboratory has a hard physical limit on how many students can work in it at once, and a large class cannot simply be placed in one. Preprocessing computes how many groups the class must be divided into so that each group fits the largest available laboratory, and creates one session per group. If the number of groups required exceeds the number of sessions available in the week, no valid arrangement exists, and preprocessing does not pretend otherwise: it records a conflict for an officer to resolve, by the means described in Section 3.7.

The third concerns **university-wide courses** — the general requirements, set by the university rather than by a department, that every student must pass before graduating. Because such a course is taken by all classes, irrespective of their programme or level, scheduling a separate lecture for each class would be wasteful and would exhaust the single lecturer who teaches it. Preprocessing instead gathers every class in the run and packs them into as few groups as the halls allow, each group's combined population fitting the largest suitable room enlarged by the same overflow threshold; each group then becomes one session. Several classes therefore sit a university requirement together in one period, and the course is taught a handful of times rather than dozens. A class too large for any hall lands in a group of its own and is flagged over capacity, exactly as a single oversized class would be.

A small number of courses, finally, need no room at all. A practical course held off-site — in a field, on a farm, or on an engineering site — is marked as such, and preprocessing builds its sessions to be placed by time alone, occupying their classes' and lecturer's periods but requiring no hall.

The output of preprocessing is a list of sessions, together with the time slots, the rooms, and the lecturers' unavailability — and a list of any conflicts that make a full solution impossible.

### 3.6.2 The Constraint Model

The scheduling problem is expressed for the CP-SAT solver as a constraint optimisation problem over boolean decision variables. For every combination of a session *s*, a time slot *t*, and a room *r*, the model defines a variable that is true exactly when session *s* is placed in slot *t* and room *r*. A valid timetable is an assignment of true and false to all these variables that satisfies every hard constraint below; the solver searches for one by systematic search, using the constraints to prune away the vast regions of the space that cannot contain a valid answer, and — as the objective described after the constraints explains — prefers among the valid timetables those that use their rooms well.

The hard constraints of Chapter 2 translate almost directly into conditions on these variables:

- **Each session is scheduled exactly once.** For every session, exactly one of its (slot, room) variables is true. This guarantees that every required meeting is placed, and placed only once.
- **No room is double-booked.** For every room and every time slot, at most one session occupies it.
- **No lecturer is double-booked.** For every lecturer and every time slot, at most one of that lecturer's sessions is placed, across all rooms.
- **No class is double-booked.** For every class and every time slot, at most one of the sessions that class attends is placed. Because a merged session is attended by several classes at once, this constraint correctly prevents any of those classes from being scheduled elsewhere at the same time.
- **Room types must match.** A session may only occupy a room whose type matches what the course requires; a laboratory session cannot be placed in a lecture hall. Any variable pairing a session with an unsuitable room is fixed to false.
- **Lecturer unavailability is respected.** A session may not be placed in any time slot the lecturer has declared unavailable; the corresponding variables are fixed to false.

Room capacity is handled slightly differently. Rather than forbidding every placement in a room smaller than the class — which, given the chronic shortage of large halls, could leave the problem with no solution at all — the model allows such a placement but marks the resulting entry as over capacity, so that the officer sees clearly where crowding has been accepted. This reflects the reality of the university, where an over-full hall is sometimes the least bad option, while still refusing to hide the fact. An off-site course, by contrast, is exempt from the room requirement altogether: its sessions are placed by time slot alone and occupy no room, so that fieldwork keeps its place on the timetable without competing for the scarce indoor halls.

The hard constraints can be satisfied by many different timetables, and not all of them are sensible: nothing in the constraints alone prevents a class of sixty from being given a six-hundred-seat hall while a joint course of four hundred is squeezed into a small room. To choose well among the valid arrangements, the model is given an **objective** to minimise. Each placement of a session in a room is charged a cost equal to the seats it would leave empty — the gap between the room's capacity and the session's population — while a placement in a room too small to hold the session is charged a far heavier penalty instead. Minimising the total cost drives the solver toward the tightest room that still fits each session, which has the effect of reserving the large halls for the large and joint sessions that genuinely need them and leaving the smaller rooms to the smaller classes. The problem is therefore not one of mere satisfaction but of optimisation: among all valid timetables, the solver seeks the one whose rooms are used most appropriately, within the time it is allowed.

The solver is given a bounded time in which to search. It returns one of a small set of outcomes: an *optimal* solution — a valid timetable the solver has proven uses its rooms as well as the objective allows — or a merely *feasible* one, valid but found before optimality could be proven; *infeasible*, meaning the constraints cannot all be satisfied and no valid timetable exists for the given data; or *unknown*, meaning the time ran out before a conclusion was reached. The crucial property is that the solver can never return an invalid timetable: any assignment it reports as a solution satisfies every hard constraint by construction, which is exactly the guarantee the non-functional requirement of correctness demands.

### 3.6.3 Postprocessing

When the solver returns a valid assignment, postprocessing writes it into the database. Each placed session becomes a *TimetableEntry* recording its course, lecturer, time slot, and the room it occupies — or no room, when the session is held off-site — and a link is created to each class that attends it. An entry placed in a room too small for its class is flagged as over capacity, and an entry that serves several merged classes is flagged as merged. After this stage the timetable exists as ordinary data that the rest of the system — the grid, the filters, the exports — can read like any other.

## 3.7 Description of the Resolution Process

It is worth drawing the preceding pieces together into a single account of how a request for a timetable becomes a published schedule, because it is in this end-to-end process that the contribution of the work, beyond the solver itself, becomes visible.

The process begins when a timetable officer creates a run, choosing the semester it covers, the faculties it concerns, and the buildings whose rooms it may use. These choices bound the problem: they fix which courses must be scheduled, which classes attend them, and which rooms and time slots are available. The officer then triggers generation. Before any work begins, the system checks that the run is complete enough to schedule and declines to start if it is not, so that effort is never spent generating from data that cannot yield a timetable. As described in Section 3.6, the system preprocesses the data into sessions, resolving shared courses by merging and large laboratory classes by splitting, and hands the result to the solver, which searches for an assignment that breaks no hard rule. A valid result is stored as a timetable; an impossible one is reported.

Where preprocessing has found a problem it cannot resolve — most commonly a laboratory class needing more groups than the week has sessions — the run carries a flagged conflict, and the officer must settle it before the timetable can proceed. The system offers two resolutions. The first, **adding a session**, gives the course an extra weekly slot so that the required groups can all be accommodated. The second, **rotating groups**, keeps the existing number of slots but alternates which group attends in which week, so that over a fortnight every group is served. The choice is the officer's, because it is a judgement about how the faculty prefers to teach, not a fact the system can determine. Once the conflict is resolved, the timetable is complete.

The complete draft then enters the coordination phase that distinguishes this system from the single-planner tools surveyed in Chapter 2. The officer submits it for review, and it cannot advance until every faculty head whose faculty it touches has approved their own portion. This is not a formality bolted onto the generator; it is the point at which accountability for the timetable is established and recorded. A head who finds a problem rejects the section, with a comment, and the run returns to the officer to be corrected and resubmitted. Only when the approvals are unanimous does the run become approved, and only then may the officer publish it.

Publication is the last step and the one that matters most to students. The published run is exposed on a public page that needs no account and is reached through a shareable link — the kind of link an officer can post in a departmental messaging group. A student opening that link narrows it to their own class through a faculty–department–level filter and sees their schedule, and only their schedule. Should a change be needed afterwards, the officer can move a session by hand, but never carelessly: as Section 3.4.4 showed, every manual move is checked for clashes before it is accepted, so the validity established at generation is never quietly lost.

Seen whole, the resolution process is a pipeline with a guarantee at each stage. A readiness check guarantees that generation is attempted only on data capable of producing a timetable. Preprocessing guarantees that the problem handed to the solver is the right problem. The solver guarantees that the timetable it returns is valid. The workflow guarantees that no timetable is published without the responsible heads having approved it. And the clash-checked editing guarantees that validity survives every later change. Each guarantee addresses one of the weaknesses identified in the problem statement of Chapter 1.

## 3.8 Partial Conclusion

This chapter has set out the analysis and design of the system. It began by stating the methodology — an iterative engineering process that built and validated the scheduling core before the system around it — and then analysed the problem into the functions the system must provide and the qualities it must possess, with correctness foremost among the latter. From that analysis it built a series of models: an entity–relationship model of the data, faithful to the faculty–department–level structure of a Cameroonian university; a use case model of the six roles and their permissions; a class model separating the domain from an independently testable solver layer; and sequence and activity models of generation, approval, and manual editing. It then described the client–server architecture that hosts these designs, the constraint model at the centre of the solver, and the resolution process that carries a request through to a published, student-accessible timetable.

The design realises the decision made at the outset: that the system should enforce the hard scheduling rules itself, by construction, and wrap that guarantee in a workflow and a data model that match how the university actually works. What remains is to show that the design works in practice. The next chapter describes how the system was implemented, presents the working result, and evaluates it against the objectives of this work and against the manual process it is intended to replace.
